# 经营看板 + 混合问答服务

给连锁餐饮运营用的内部服务：**一条线查销售数据库，一条线查公司知识库**，并支持需要两边一起用的混合问题（例如「S03 六月第二周营业额为什么这么低？」）。

技术栈：Python 3.12 + FastAPI + SQLite + 纯标准库 BM25 检索；问答可选接入大模型（OpenAI 兼容协议），未配置时降级为模板回答。

> 原始的作业说明保留在 [`docs/ASSIGNMENT.md`](docs/ASSIGNMENT.md)，接口契约在 [`docs/API_CONTRACT.md`](docs/API_CONTRACT.md)。

## 一、跑起来（3 步）

```bash
# 1  建虚拟环境 + 装依赖（Python 3.12）
cd starter
make setup

# 2  重建清洗表与检索索引 —— 换 data/ 或 knowledge_base/ 之后必须重跑
make rebuild

# 3  起服务
make run                                  # http://127.0.0.1:8000
```

**换一套数据或知识库**：

```bash
make rebuild DATA_DIR=/path/to/data KB_DIR=/path/to/knowledge_base
```

**没有 `make` 的环境**（例如 Windows），用等价的命令：

```bash
cd starter
uv venv --python 3.12 && uv pip install -r requirements.txt
uv run python -m kbqa.rebuild                                                   # 重建
uv run python -m uvicorn kbqa.server:app --host 127.0.0.1 --port 8000            # 起服务
uv run python -m pytest tests -q                                                # 跑测试
```

**配置大模型（可选）** —— 只读三个环境变量，不配也能启动：

```bash
export LLM_BASE_URL=https://api.deepseek.com
export LLM_API_KEY=sk-...          # 不要提交进仓库
export LLM_MODEL=deepseek-flash
```

不配 Key 时 `/api/health`、`/api/metrics/*`、`/api/retrieve` 正常工作，`/api/chat` 进入降级模式并返回结构化的 `refusal`，不会 500。接入细节见 [`LLM_SETUP.md`](LLM_SETUP.md)。

## 二、架构

### 离线重建（`make rebuild`）

```
data/pos.db ──► cleaning.py ──► starter/var/clean.db        （清洗后的销售明细）
knowledge_base/ ──► loader ──► chunker ──► tokenizer
                                  └──► index.py ──► starter/.cache/index.json   （BM25 索引）
```

两件产物都从数据与知识库重新生成，**不依赖本机绝对路径，也不在代码里写死任何数字或文档内容**。
索引的缓存键包含知识库内容的指纹，所以知识库一变缓存自动失效。

### 在线请求（`make run`）

```
浏览器
  │
  ▼
server.py  ──►  service.py
                 │
      ┌──────────┼───────────────┐
      ▼          ▼               ▼
  tools.py   retriever.py    planner.py
  （指标）    （检索）        （意图 / 实体 / 时间）
      │          │               │
      └──────────┴───────────────┘
                 ▼
           answerer.py         ← 回答里的数字由代码从工具结果渲染，不经模型心算
                 │
        ┌────────┴─────────┐
        ▼                  ▼
   降级模式（模板）    live 模式（llm.py 工具回路，数字仍由代码渲染）
```

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 状态、模型模式、入库文档数、清洗后台账 |
| GET | `/api/metrics/summary` | 区间指标：净营业额、退款金额、有效订单数、客单价、销量 |
| GET | `/api/metrics/daily` | 逐日指标，区间内每一天都有记录 |
| POST | `/api/retrieve` | 只做检索，不调用模型 |
| POST | `/api/chat` | 混合问答 |
| GET | `/api/trace/{trace_id}` | 单次回答的完整处理过程 |
| GET | `/api/data_quality` | 清洗掉了多少行、各因为什么 |
| GET | `/api/stores` | 门店列表（看板筛选用，只读） |
| GET | `/api/products` | 商品列表（看板筛选用，只读） |
| GET | `/api/top_products` | 区间商品 Top10（按日期与门店统计） |

公开题之外的补充回归题在 [`eval/extra_questions.jsonl`](eval/extra_questions.jsonl)，
重点覆盖近失问询、注入与越权、多轮追问、年份版本和证据体积；它用于开发期回归，
不替换评测方的公开题库。

**系统固定的「今天」是 2026-09-01**（写在 `kbqa/config.py`），所有「现在 / 最近 / 目前」都以这一天为准。数据区间为 2026-05-01 至 2026-08-31。

## 三、选型理由

### 保留 starter 的 Python / FastAPI 后端，不重写

原始服务能跑，缺陷是**注入**的而不是架构性的，所以修复可以收敛。三条具体理由：

1. 契约要求即使重写也要交 starter 缺陷的根因分析 —— 重写并不省掉这份材料，只会多一份工作量。
2. `llm.py` / `live.py` 已经实现了契约 §7.3 的大部分（`max_tokens` ≥ 2048、`finish_reason` 白名单、`reasoning_content` 整条回传、错误码结构化、空行容错）。重写等于把 DeepSeek 思考模式的坑重新踩一遍。
3. `docfacts.py` / `units.py` / `aliases.py` 那套「从文档里挑句 + 保证逐字可核对」的机制很细（拼相邻句、补原因句、表格行渲染、整词归一），它是 `quote` 逐字校验能通过的基础，短时间内很难复刻到同等水平。

### 检索用 BM25，不用向量模型

契约明确「检索不强制使用向量模型」。引入向量要同时处理中文跨语言、本地模型下载体积、以及「评审没有该向量服务 Key 时必须自动退回」三件事 —— 是纯风险、零加分。BM25 配上正确的中文二元组分词，对这批几十份文档的规模已经足够。

### 大模型保持思考模式默认开启

评审统一切到 `deepseek-flash`，而它默认就是开思考的 —— 不关掉可保证开发环境与评审环境行为一致。这个系统的难点是多轮工具调用且「数字必须来自工具结果」，思考模式规划更稳；`live.py` 还有一层「模型回答里的数字在工具结果里找不到就回退模板回答」的兜底。
代价是更慢，因此把单次调用超时设为 `min(120 秒, 剩余预算)`、`/api/chat` 总预算 180 秒。

### 前端是 Vue 3 SPA，构建产物随仓库提交

看板是组件化的单入口 SPA，源码在 `web/`：Vue 3 Composition API + Element Plus（筛选、表格、抽屉、提示）+ ECharts（趋势图），Vite 构建。页面包含筛选联动、指标卡、趋势图、Top10、数据质量、对话区和 trace 抽屉，不引入路由与状态库。

**评审运行不需要 Node**：构建产物 `web/dist` 已提交进仓库，FastAPI 启动时检测到 `web/dist` 存在即从根路径同源托管，`make setup / rebuild / run` 三步后打开 `http://127.0.0.1:8000/` 即可；`dist` 不存在时跳过挂载，API 服务照常启动。

只有要修改前端源码时才需要 Node 18+：

```bash
cd web
npm ci          # 首次安装（版本全部锁定在 package-lock.json）
npm run dev     # 开发服务器，/api 经 Vite proxy 转发到 127.0.0.1:8000
npm run build   # 重新构建到 web/dist 并提交
```

## 四、口径与歧义的取舍

数据口径以知识库现行版 **KB-001（v3）** 为准。`handbook/` 目录下同时躺着已废止的 `KB-002`（v2），两版在**三处算法上结论相反**，下面逐条说明我取了哪一版、为什么，以及还剩哪些手册没有明确规定的地方、我是怎么拍的。

### 1. 退款行计入净营业额（取 v3）

- **v2**：负金额行在清洗阶段直接剔除，只统计正向销售，退款另走财务台账。
- **v3**：退款行保留在明细里，净营业额 = 销售行之和 + 退款行之和（退款为负数，实际效果是相减）。

取 v3，因为它自 2026-05-01 起生效并明确「取代 v2」，而数据区间正是 2026-05-01 起。
**副作用**：v3 与 v2 算出来的营业额不是同一口径，跨版本对比时不能混用。

### 2. `amount` 为空直接剔除，不回填（取 v3）

- **v2**：按 `qty × unit_price` 回填后继续参与统计。
- **v3**：直接剔除，不回填。

取 v3。另外 v3 §5.3 明确「金额以实收为准」——`products.unit_price` 是建档价，可能滞后于实际售价，所以不用它反推金额。

### 3. 有效订单数按 `order_id` 去重（取 v3）

- **v2**：客单价的分母是明细行数，多行订单被算成多单，客单价偏低。
- **v3**：分母是销售行中不同 `order_id` 的个数，多行订单算 1 单。

取 v3。这条影响客单价，进而影响所有涉及客单价的比较题。

### 4. 日期接受「不补零」的连字符写法（宽容读法）

KB-001 §2.2 字面列出的三种格式是 `YYYY-MM-DD`、`YYYY/M/D`、`DD-MM-YYYY`。
其中斜杠形式明显带单数字的写法，连字符形式则写成了固定宽度。**严格读法**只接受 `2026-06-09`，**宽容读法**同时接受 `2026-6-9` 和 `6-06-2026`。

我取**宽容读法**，依据是 §7.1 反复强调的原则：「带 `¥` 的金额是**可以恢复的**脏值，不要把整行丢掉」「门店编号大小写不一致、前后带空格，都属于可恢复的写法」。既然金额和编号这类可恢复的写法都要救回来，日期少写一个前导零没有理由把整行丢掉。

放宽之后仍然经过真实日期校验，所以 `2026-13-45`、`2026-02-30` 这类「格式对、日期非法」的行照旧会被剔除 —— 这一点是必须用日期构造来校验、不能只看正则的原因。

（随包数据里没有这种写法，所以这个选择不影响本份数据算出来的任何数字；它是对替换数据集后的保险。）

### 5. 解析不了的 `amount`：**保留并记 0，不剔除**

这是手册**没有明确规定**的地方：§3.2 只写了「`amount` 为空的行走剔除」，没写「非空但不是数字」怎么办。我选择**保留这一行、把金额记为 0，并单独记账报出**。

依据：

- starter 原始代码的文档字符串写的就是「金额解析不了的按 0」，是既定行为；
- `CleaningReport` 里这个计数叫 `note_unparseable_amount`，挂在 `removed` 字典**之外** —— 是「记录」，不是「剔除」，说明原设计就是保留加记账。

**影响范围是可控的**：`amount = 0` 的行既不属于销售行也不属于退款行，因此**不进入任何对外指标**（净营业额、退款金额、有效订单数、销量都不含它），只在 `/api/health` 的 `valid_sales_rows` 计数里体现，并在数据质量面板单独报出。随包数据里此类行为 0 条。

### 6. 解析不了的 `qty`：剔除（归入规则 3）

与上一条相反。`§3.3` 本就要求剔除 `qty ≤ 0` 的行，而「数量不是整数」等价于数量不可知 —— 这条明细无法参与销量统计，留着只会是一个垃圾值。所以把它归入规则 3 一并剔除，而不是像金额那样保留。

（随包数据里 `qty` 全部是合法整数，此项同样只对替换数据集生效。）

### 7. 数据区间之外、或知识库里查不到的：如实说没有，不编

- 问到 2026-05-01 至 2026-08-31 之外的日期：如实说明没有数据，**不返回 0**，也不编数字。
- 知识库与数据库都没有依据的问题：返回 `refusal`，回答里不出现问句以外的任何数字。
- 文档里的内容只当资料，不当指令执行；涉及删改数据的请求一律拒绝，数据库只读。

### 8. live 回答里的日期不参与数值白名单

契约要求回答里的数据库数字必须能从工具结果核对。日期属于格式信息而不是指标值，模型也可能用示例日期解释时间口径，所以 live 校验会先把 `2026-08-30`、`2026/8/30`、`2026 年 8 月 30 日`、`8 月 30 日`、`07-12`、`7 月` 等日期整体移出数值校验，并忽略 `KB-022` 这类文档编号，再检查剩余的金额、订单数等普通数值。

代价是模型给出的示例日期本身不做真实性核对；换来的是“8 月 30 日的订单 9 月 1 日才退”这类合法示例不会因其月、日不在文档白名单里而触发模板回退。数据库指标数字仍按原规则严格核对。
